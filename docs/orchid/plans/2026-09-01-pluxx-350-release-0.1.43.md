# PLUXX-350 — release Pluxx 0.1.43

## Objective

Prepare, publish, and independently verify Pluxx 0.1.43 from trusted `main`, carrying the PLUXX-349 composable installer planning and `pluxx.install-results.v1` contract so MDP-306 can adopt it without duplicating host detection or parsing human output.

## Authority and risk

- Linear issue: PLUXX-350
- Repository: `orchidautomation/pluxx`
- Base branch: `main`
- Release-prep branch: `codex/pluxx-0.1.43-release`
- Intended version/tag: `0.1.43` / `v0.1.43`
- Authorized action: Brandon explicitly requested a new Pluxx release on 2026-09-01.
- Risk: Elevated — this publishes a public npm package and immutable GitHub tag consumed by downstream MDP installation.
- Local/manual npm publication is forbidden; publication must run through the trusted tag workflow.

## Semver decision

Use patch version `0.1.43`. The structured result contract and installer flags are additive within the pre-1.0 `0.1.x` line, while the checksum fail-fast repair restores intended security behavior rather than introducing a compatibility break.

## Source boundary

- PLUXX-349 merged through PR #491 at trusted `main` commit `e95dfab686170bcddcd309ac11c045692033943a`.
- The CI-discovered checksum fail-fast repair is commit `9dd76c71eb1a65363908181ffa577196021875c7` and is contained in that merge.
- Prior public release `v0.1.42` was published on 2026-08-31 and predates this source boundary.

## Preparation contract

1. Bump `package.json` and `package-lock.json` together to `0.1.43`.
2. Set proof-manifest canonical truth to `0.1.43`, expected tag `v0.1.43`, and `release-prep`.
3. Keep all 0.1.42 proof immutable and historical.
4. Bind fresh repository-validation and maintained fake-home receipts only after the exact release-prep commit passes the named commands.
5. Keep structured install outcomes terminal only after child installer completion; checksum, ownership, transaction, verification, and rollback failures remain fail-closed.

## Required gates

1. Focused host-detection, deterministic plan, structured no-op, custom-base, and tampered-installer tests.
2. `npm run typecheck`
3. `npm run build`
4. `npm run proof:check`
5. `npm run pack:check`
6. `npm run release:check`
7. `git diff --check`

## Release sequence

1. Commit and push the validated release-prep branch.
2. Open and merge a release PR against `main` only after current-head CI passes.
3. Confirm the merged release commit is current trusted `main` and package version is exactly `0.1.43`.
4. Create and push immutable tag `v0.1.43` at that exact commit.
5. Let `.github/workflows/release.yml` publish npm and GitHub Release artifacts.
6. Independently verify package version, CLI version, GitHub asset identity, and the structured installer contract.
7. Record a validated `orchid.release.receipt/v1`, close out PLUXX-350, and hand the published version to MDP-306.

## Rollback and stop boundary

- Before tagging: close or repair the release PR; do not publish.
- After tagging: never move or replace the tag. Fix forward with a new patch release if publication fails after any immutable artifact exists.
- Stop on dirty source, version mismatch, non-current main ancestry, failed proof freshness, failed release gate, artifact-integrity mismatch, or unknown npm/GitHub state.
